## What shipped

This is the run-control and reproducibility pass. It adds the controls that turn
a single training job into a small experiment, and records enough about each run
to tell whether two runs are actually comparable.

### Run control

- **Comparison board.** Two to four runs share one loss axis, with their
  hyperparameters, dataset and seed values diffed beneath the chart. The board
  marks a winner and flags the selected runs whose stored dataset fingerprints do
  not agree.
- **Batch queue.** Several configurations can be queued to run one after another
  on the GPU, and the queue survives a UI reload instead of disappearing with
  the page.
- **Tags, notes and search.** A run can carry a label such as `baseline` or
  `lr test` and a one-line note. Both are written to the run record in the
  database, so they survive a reload and are visible to any client. History and
  the comparison board can filter by query, tag, model or dataset.
- **Throughput and ETA.** The live progress view reports tokens per second,
  steps per second, elapsed time, projected finish and GPU-hours consumed.
- **Failure post-mortem.** A failed or OOM-killed run gets a card that names the
  likely cause and the concrete setting to change, rather than leaving the user
  with the log.
- **Early-stop parent guard.** A child run can be compared with a parent's
  recorded loss. At each observed step the guard reads the latest parent point at
  or before that step; if the child fails to beat it by the configured
  `min_delta` within the patience window, the guard signals the run to stop. It
  stays off unless the user opts in, names the parent and threshold it is
  applying, and runs through the existing progress observer rather than a second
  monitor.

### Reproducibility

- **Dataset and tokenizer fingerprints.** Start hashes the dataset files under
  the source path and the tokenizer files, then stores both fingerprints with
  the run. When the content behind a comparable run differs, the comparison
  surfaces can say so. A streaming dataset, or a Hub dataset that is not on disk,
  records an `unavailable` fingerprint with the reason instead of a fabricated
  hash.
- **Full-run disk preflight.** Before Start, the estimate covers base weights,
  optimizer state, every checkpoint and the final save, and compares the total
  with free space on the output volume. An over-budget run is refused with a
  component breakdown and the shortfall. If the parameter count or run shape is
  unknown, the check says so instead of inventing a number.
- **Resume safety.** Continuing from a checkpoint verifies the adapter, tokenizer
  fingerprint, dataset fingerprint and optimizer state against the stored run.
  A mismatch is named and blocks the continue instead of letting the run
  proceed silently.
- **Reproducibility bundle.** The config, fingerprints, seed and package
  versions can be exported together as one replayable recipe.

### Evidence and housekeeping

- **Model-card lint.** Before export or publish, the README is checked for the
  base model, license, dataset description and evaluation evidence. The card
  reports only what it can actually read from the README and names the fields
  that are missing; it does not supply a license or an eval number.
- **Loss-chart event markers.** Checkpoint saves, resumes, learning-rate changes
  and the anomaly callout appear as vertical markers on the existing loss chart,
  so a spike has visible context.
- **Benchmark trend.** Benchmark records gain a trend against the previous best,
  with regressions flagged instead of leaving the records as isolated rows.
- **Retention preview.** Cleanup can propose keeping the best few runs per
  project and preview exactly which artifacts would be kept or deleted before
  the guarded delete runs.

### Webhooks and settings

Settings now includes webhook endpoint configuration with delivery status. The
loss-anomaly tracker is shared by the parent guard and the terminal notification
path, so the same run history drives both.

## How it was built

The installers were built and signed, then staged in `release-out/` before
anything was uploaded:

```bash
python scripts/release_x8_local.py --version 2026.6.1 --variants all --dry-run
```

The dry run compiles each flavor separately and assembles the signed manifest
without uploading. `gh` was not logged in on this machine, so the publish step
used the credential `git` already had:

```bash
tok=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill \
  | sed -n 's/^password=//p')
GH_TOKEN="$tok" python scripts/release_x8_local.py --version 2026.6.1 \
  --variants all --skip-build --notes-file /tmp/x8-2026.6.1-notes.md
```

`--skip-build` uploaded the already-staged installers and regenerated
`latest.json`; it did not reuse an older version's manifest. Authenticode is
skipped locally (`UNSLOTH_SKIP_AUTHENTICODE=1`). The Tauri updater signature was
still generated with `studio/src-tauri/x8-updater.key` and is what clients
verify.

## Limits

The new UI was typechecked and bundled, and its pure logic is covered by the
focused tests above, but it was not clicked through in a running desktop build.
The full frontend suite and the known-red sidebar families were not re-run for
this release.

Fingerprints are file-level hashes. A Hub dataset must be present locally before
it can be hashed, and a streaming source records `unavailable` rather than a
digest. Disk estimates are only as specific as the model metadata supplied; an
unknown parameter count returns an `unknown` report instead of a guess.
